## 1. 产品概述

### 1.1 背景

班主任每学期都要排座位。现状是用 Excel 手工摆、靠记忆平衡身高/性别/关系/特殊需求，改一次要重排一遍，且无法解释"为什么这么排"。老师真正需要的不是一张表，而是一个**能被反复调整、并且排得有理由**的排座工作台。

### 1.2 一句话定位

> 导入名单 → 选座位布局 → 勾几个规则 → 一键生成一张好看的教室座位图，然后像摆积木一样拖着改。

AI 只做一件但很关键的事：**把老师随手写的"话多、坐不住、数学弱、和谁都能聊"这类自由描述，理解成语义标签并算出谁和谁互补**，再交给确定性求解器去落座。

### 1.3 产品目标

| 目标 | 衡量方式 |
| --- | --- |
| 排座从"半小时"降到"2 分钟" | 首次排座（导入到出图）≤ 3 分钟，二次重排 ≤ 30 秒 |
| 排出来的结果老师愿意直接用 | 生成后的人工拖动次数 ≤ 3 次为「可接受」，≥ 85% 的场景达标 |
| 规则可解释 | 每个座位可查看"为什么被安排在这里"的规则命中说明 |
| 特点能被"听懂" | 老师自由填写的特点经语义归并后，同义表述合并准确率 ≥ 90%（人工抽检 100 条） |
| 操作手感好 | 拖动全程 60fps，无掉帧、无错位；撤销/重做随时可用 |

### 1.4 非目标（本期不做）

- 不做账号体系、云同步、多端协同（数据只存本地）。
- 不做学生成绩管理、考勤、家校沟通。
- 不做"每周自动轮换座位"（轮换属于二期规划，见 §12）。
- 不做移动端 App；只有 Windows 桌面安装包。
- **不使用大模型直接生成座位**：LLM 不参与落座决策，只做语义理解；求解由确定性引擎完成（理由见 §5.2）。

## 2. 用户与使用场景

### 2.1 用户画像

| 角色 | 描述 | 核心诉求 |
| --- | --- | --- |
| 班主任（主用户） | 30–50 岁，Excel 熟练，非技术背景 | 快、结果合理、能改、能打印 |
| 年级组长/教务处（次要） | 需要汇总各班座位表 | 统一格式导出 |

### 2.2 典型场景

**场景 A：开学第一次排座**
老师打开软件 → 新建班级「高二(3)班」 → 导入 48 人名单 xlsx → 选择预设布局「双人桌 · 4 组 · 6 排」 → 勾选规则（身高优先前排、男女同桌、特点互补、2 名学生固定第一排）→ 点击「智能排座」→ 3 秒后出图 → 手动把 1 个爱讲话的学生换到角落 → 保存为「方案 A」。

**场景 B：临时调座**
同桌两人闹矛盾。老师打开上周的方案，把其中一个学生拖到空位/与另一人交换，软件实时提示"该调整会影响 2 条规则"→ 确认 → 导出 PDF 打印贴墙。

**场景 C：领导检查/家长会**
老师切换到「学生视角」核对左右是否排反，然后导出高清 PNG 发到群里。

## 3. 核心概念与术语

| 术语 | 定义 |
| --- | --- |
| **班级 Class** | 一份学生名单 + 一份座位布局 + N 套排座方案 |
| **座位槽 Slot** | 画布上的一个可坐位置，有行号、列号、所属桌组、区域标签 |
| **桌型 Desk** | 单人桌（1 人/桌）或双人桌（2 人/桌，互为同桌） |
| **布局 Layout** | 行数 × 列数 × 桌型 × 过道 × 讲台方向 × 空位/禁区 的组合 |
| **排座方案 Plan** | 某个布局下的一次完整分配结果，可保存多份、可对比 |
| **规则 Rule** | 一条排座约束：条件（谁）+ 动作（要/不要怎样）+ 强度（必须/权重） |
| **硬约束 Hard** | 违反即结果不合法（如一槽一人、固定座位、身高 >190 不得坐前两排） |
| **软约束 Soft** | 尽量满足，用权重折算成得分 |
| **满足度** | 某条规则被满足的比例（0–100%），用于结果解释与调参反馈 |

## 4. 功能需求

优先级：**P0** = MVP 必须；**P1** = 首个正式版；**P2** = 后续增强。

### FR-1 班级与学生数据管理（P0）

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| FR-1.1 | 班级列表 | 支持新建/重命名/复制/删除班级；显示人数、最近更新时间 |
| FR-1.2 | 学生字段 | 学号（唯一，可空则自动生成）、姓名（必填）、性别（男/女/未填）、身高（cm，数值，可空）、特点标签（多选+自定义文本）、备注、固定座位（可选） |
| FR-1.3 | 特点标签体系 | 既有内置标签组（性格：活跃/安静/内向/外向；学习：学科强弱、需要帮扶；行为：爱讲话/需要关注/自律），也支持**自由文本**；AI 会自动把自由文本归并与补全（见 FR-4.4），老师无需先整理标签 |
| FR-1.4 | 名单表格视图 | 表格式增删改，支持排序/筛选（按性别、身高区间、标签）、批量打标签、批量删除 |
| FR-1.5 | 学生搜索 | 顶部搜索框按姓名/学号秒搜，画布上对应座位高亮脉冲 |
| FR-1.6 | 数据校验 | 学号重复、姓名为空、身高越界（100–230）、性别未填 → 导入/保存时给出逐行错误清单，可修正后继续 |

**验收**：新建班级 → 手动加 3 人 → 改身高 → 打标签 → 删除 1 人，全程无需刷新，列表与画布数据一致。

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| FR-2.1 | Excel/CSV 导入 | 支持 `.xlsx / .xls / .csv`；拖文件到窗口即可导入 |
| FR-2.2 | 表头智能映射 | 自动识别"学号/学生姓名/性别/身高/特点"等同义表头；识别不准时提供手动下拉映射界面，展示前 5 行预览 |
| FR-2.3 | 模板下载 | 提供标准模板 xlsx 下载，含表头说明与 3 行示例 |

| FR-2.6 | 容错 | 空行跳过；性别写"male/女/1/2"等可归一化；身高带单位 `172cm` 可解析；失败行汇总报告 |

### FR-3 座位布局设计（P0）

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| FR-3.1 | 预设布局 | 内置预设：单桌 5 列 × 6 排（每人独立，无同桌）、双桌 4 组 × 6 排（48 人）、双桌 3 组 × 6 排（36 人）、U 型（P2）、分组岛式（P2） |
| FR-3.2 | 自定义布局 | 可调：行数（1–10）、列数/组数（1–8）、桌型（单人/双人）、过道位置（组间自动留缝，可指定额外过道）、讲台所在边（上/下） |
| FR-3.3 | 空位与禁区 | 点击槽位可设为「空位（不坐人）」；整块区域可设为禁区（如讲台旁不放桌） |
| FR-3.4 | 编号与标注 | 显示/隐藏：行号、组号、座位序号；支持"第 1 排靠窗"这类区域标签 |
| FR-3.5 | 容量校验 | 座位总数 < 学生数时阻止排座并提示差值；座位数 > 学生数时空位高亮显示 |
| FR-3.6 | 布局实时预览 | 调整参数时画布即时重绘（带过渡动效），无需点保存 |

### FR-4 智能排座引擎（P0）

#### FR-4.1 内置规则（可勾选、可拖动排序、可调权重 1–100）

| 规则 | 逻辑 | 默认权重 |
| --- | --- | --- |
| 身高：矮的优先前排 | 按身高升序与排号建立相关度，后排应高于前排（同一排内不强制） | 70 |
| 性别搭配：男女同桌/相邻 | 双人桌优先一男一女；单桌模式退化为"男女交替相邻" | 60 |
| 特点标签互补 | 不再使用写死的关系对，改由**语义引擎**计算同桌/相邻的互补分（见 FR-4.4 与 §5.2），支持任意自由文本 | 65 |
| 特殊需求优先前排 | 标签含「近视/视力差/听力弱/身高<140」→ 前排加权 | 80 |
| 特殊需求优先后排 | 标签含「身高>185/高个」→ 后排加权；身高 >190 视为硬约束（不得坐前两排） | 硬 |
| 避免同标签聚集 | 同一标签（如"爱讲话"）同排相邻则扣分 | 55 |
| 随机打散 | 在满足上述规则前提下增加随机扰动，避免每次结果完全一样 | 20（仅影响多样性） |

#### FR-4.2 自定义规则（核心差异化，P0）

老师用「条件 + 动作 + 强度」三步搭建，无需写代码；**自定义规则的优先级高于所有内置软规则**。

- **条件（谁）**：字段（姓名/学号/性别/身高/标签/备注）+ 运算符（等于、包含、大于、小于、属于…）+ 值；支持 AND / OR 组合，最多 3 层。
- **动作（怎么排）**：

| 动作 | 说明 | 强度选项 |
| --- | --- | --- |
| 固定到指定座位 | 如"张三固定第 1 排第 1 座" | 必须 |
| 与某人同桌 | 两人绑定为同桌（双桌模式） | 必须 / 强烈 |
| 不与某人相邻 | 两人不得同桌、上下左右相邻 | 必须 / 强烈 |
| 优先安排到区域 | 靠窗 / 靠门 / 中间 / 前排 / 后排 / 指定排 | 强烈 / 普通 |
| 禁止安排到区域 | 同上取反 | 必须 / 强烈 |
| 同组相邻 | 如"学习小组 3 人需相邻" | 强烈 |
| 按字段顺序填充 | 如"按学号顺序从左到右、从前到后" | 强烈 |
| 男女分列 | 整列只放某一性别 | 强烈 |

- **强度定义**：`必须`（硬约束，不满足则排座失败并说明冲突）、`强烈`（权重 90）、`普通`（权重 60）。权重可微调 1–100，但自定义规则权重池独立于内置规则，保证"自定义优先"。
- **规则模板**：常用规则一键添加（如"两个爱讲话的学生不相邻"、"近视学生坐前三排"、"身高 185 以上坐后三排"）。
- **冲突检测**：保存规则时即时检测互斥（如 A 固定 1 排 1 座，B 也固定 1 排 1 座），提示冲突并提供修改入口。

**验收**：新建规则"张三 与 李四 不与相邻（必须）"→ 排座结果中两人不相邻；故意设两条互斥的"必须"规则 → 排座前提示冲突，不允许生成。

#### FR-4.3 排座执行与结果反馈（P0）

| 编号 | 需求 |
| --- | --- |
| FR-4.3.1 | 「一键排座」按钮，计算中显示进行态（进度/扫描动效），耗时 > 800ms 显示可取消 |
| FR-4.3.2 | 结果页展示总览：规则满足度环形图/条形图、未满足项列表（哪条规则、影响几人） |
| FR-4.3.3 | 点击座位可查看「安排理由」：命中的规则、加减分、与谁同桌/相邻 |
| FR-4.3.4 | 「再排一次」（换随机种子）与「沿用上次结果优化」（在当前结果上只做局部优化） |
| FR-4.3.5 | 硬约束无法满足时，明确告知是哪条规则/哪个学生，给出一键"降级为强烈"的修复建议 |
| FR-4.3.6 | 排座结果自动成为当前方案，未保存前标记「未保存」 |

#### FR-4.4 特点语义引擎（AI 环节，P0）

定位：**AI 是"翻译器"，不是"排座器"**。它只负责把自由文本变成可计算的语义结构，最终落座仍由确定性求解器完成。

| 编号 | 需求 |
| --- | --- |
| FR-4.4.1 | 自由文本输入：特点支持自然语言（"数学拔尖但坐不住"、"和谁都能聊两句"、"需要老师多盯"），单条 ≤ 50 字，一人可多条 |
| FR-4.4.2 | 标签抽取：云端 LLM（硅基流动）按受限 JSON Schema 输出（标签名、类别、极性 positive/negative/neutral、强度 1–3）；返回不合法时自动重试 1 次，仍失败则回退内置词典 |
| FR-4.4.3 | 语义归并：所有标签文本调用云端 Embedding（`BAAI/bge-m3`，1024 维），余弦相似度 ≥ 0.82 归入同一语义簇，簇名取高频表述；"话多 / 爱说话 / 话痨 / 爱聊天"自动合并 |
| FR-4.4.4 | 互补度矩阵：预计算学生两两之间的特点互补分并缓存（n ≤ 80，约 3.2k 对），排座时 O(1) 查表 |
| FR-4.4.5 | 人工校正优先：AI 给出的类别/极性以 chip 展示，老师可改；本地覆盖表的优先级高于 AI 结果，且不会被下次归并覆盖 |
| FR-4.4.6 | 离线降级：未联网/未配 Key/接口失败 → 使用内置同义词表（约 200 组）+ 关系对（活跃↔安静、强科↔弱科）继续排座，界面明确标注"本地语义模式" |
| FR-4.4.7 | 缓存与增量：以「模型名 + 文本 hash」为 key 缓存向量与抽取结果；只对新增文本发请求，单班首次语义处理 ≤ 3s |
| FR-4.4.8 | 隐私最小化：上传内容**仅限特点文本**，绝不包含姓名、学号、班级名；"严格脱敏"开启时，文本中的姓名替换为"某同学" |
| FR-4.4.9 | 可解释可视化：规则面板展示「语义簇地图」——簇内代表标签、人数、极性，让老师看到 AI 到底理解成了什么，并可直接合并/拆分簇 |

**验收**：输入 30 条口语化特点 → 归并出人工认可的语义簇（抽检准确率 ≥ 90%）→ 排座结果中"特点互补"规则出现非零得分；断开网络后仍能完成排座，且界面提示"本地语义模式"。

**调用量预估**：单班首次约 30–60 次 embedding + 1 次标签抽取，之后仅增量；按硅基流动定价，单班单次成本可忽略（< 0.01 元量级），排座本身零调用。

| FR-5.11 | 多选批量 | `Shift` 框选多个座位 → 批量设为空位/批量固定（P1） |

### FR-6 视角切换（P1）

- 两种视角：**讲台视角**（默认，老师站在讲台看学生，第 1 排在画面下方）与**学生视角**（学生看讲台，第 1 排在画面上方）。
- 切换时整块画布 3D 翻转 600ms（perspective 1200px，带轻微位移），座位内容同步镜像左右。
- 画布一角常显当前视角标签，导出时按当前视角输出。

**验收**：切换视角后左右关系正确镜像；导出图片与屏幕所见一致。

### FR-7 方案管理与历史（P1）

| 编号 | 需求 |

## 5. 排座算法设计

### 5.1 问题建模

给定：
- 学生集合 `S`（n 人），每个学生带属性（性别、身高、标签集、固定需求）。
- 槽位集合 `P`（m 个，m ≥ n），每个槽位带（排号 r、组号 c、桌组 id、区域标签、是否禁区）。
- 规则集合 `R` = 硬约束 `R_hard` + 加权软约束 `R_soft`（含自定义优先池）。

求：双射 `f: S → P'`（P' ⊆ P，|P'| = n），使

```
Score = Σ_{r ∈ R_soft} w_r · sat_r(f)   // sat_r ∈ [0,1]，归一化
```
在满足全部 `R_hard` 的前提下最大化 Score。

### 5.2 为什么 AI 不直接排座（关键技术决策）

| 方案 | 硬约束保证 | 可复现 | 60 人耗时 | 可解释 | 结论 |
| --- | --- | --- | --- | --- | --- |
| LLM 直接输出座位表 | 无法保证（可能重座/漏座） | 否，两次结果不同 | 3–30s | 理由为事后编造 | 不采用 |
| 确定性求解器（贪心 + 模拟退火） | 100% 可验证 | 是（记录 seed） | < 1.5s | 每分可追溯到规则 | **采用** |
| 混合：LLM 只做语义/规则编译，求解器落座 | 100% | 是 | < 2s | 是 | **本期采用语义部分** |

核心原因：排座是一个**双射约束下的组合优化问题**（每人恰好一个座位、固定座位必须命中、两人必须/不得相邻）。LLM 逐 token 生成，既无法在生成过程中校验全局约束，也无法保证"改一个人只影响局部"。而这类问题恰好是确定性优化器的强项。

因此 AI 的边界被严格限定为：**理解人的语言 → 输出结构化语义 → 交给引擎计算**。AI 不接触座位坐标。

### 5.3 特点语义评分（AI 环节）

**第一步：抽取。** 每条自由文本 → LLM 输出 `{tag, category, polarity, strength}`，category ∈ 性格 / 行为 / 学习 / 其他，polarity ∈ 正 / 负 / 中性，strength ∈ 1–3。

**第二步：归并。** 对标签文本取 embedding（1024 维），余弦相似度 ≥ 0.82 归为同一语义簇；簇中心取成员向量均值。学生画像 = 其标签簇集合 `C_s`。

**第三步：互补映射。** 关键点：**"互补"不是"相似"，方向由标签类别决定**——纯向量相似度无法判断"相似是好事还是坏事"，所以必须保留 category / polarity 作为先验。

| 标签类别 | 互补的定义 | 计分 |
| --- | --- | --- |
| 性格 / 行为 | 差异即互补 | `1 − cos(簇中心向量)`，同簇记 0 |
| 学习 | 强弱搭配 | 极性相反 +1.0，同极 −0.5，中性 0.3 |
| 其他 / 未分类 | 避免同质聚堆 | 同簇 −0.3，跨簇 0 |

- **距离衰减**：同桌权重 1.0，前后左右相邻 0.6，同排隔位 0.25。
- **归一化**：单个学生的互补分取与其关联座位的最大值；全班归一化到 [0,1] 后乘以规则权重（默认 65）计入总分。
- **降级**：离线时用内置同义词表把文本映射到粗粒度簇，公式不变，仅精度下降。
- **不参与硬约束**：语义分永远是软约束，任何"必须"级规则优先于它。

### 5.4 求解流程

0. **语义预处理**：读取特点文本 → 命中缓存直接用 → 未命中则批量请求抽取/embedding → 生成互补度矩阵；失败则切本地同义词表（不阻断排座）。
1. **槽位图构建**：根据布局生成槽位，计算邻接关系表（同桌、上下左右、同排、同组、靠窗/靠门），预计算便于后续 O(1) 判定。
2. **硬约束预分配**：固定座位 / 同桌绑定 / 禁止相邻 / 身高硬限制中"必须"的规则先落子；若冲突则立即返回冲突清单，不进入求解。
3. **贪心初始解**：按"约束度高的学生优先"（固定 > 特殊需求 > 标签特殊 > 普通）依次放入当前得分最高的槽位。
4. **局部搜索优化**：在初始解上做成对交换（2-swap）迭代爬山；接受准则用模拟退火（初温 T0=1.0，指数降温），
   - 只对"涉及变化座位"的规则增量重算，避免全量评分；
   - 达到 `maxIter`（默认 8000 次交换或 800ms）或连续 600 次无提升则停止；
   - 随机种子可复现（记录 seed，便于"同样的设置得到同样的结果"）。
5. **结果输出**：座位分配 + 每条规则的满足度 + 每个学生的安排理由（Top 3 命中规则与扣分项）。
6. **可解释**：所有评分项都保留可读文本，前端"安排理由"直接消费。

### 5.5 冲突与降级策略

- 存在互斥硬约束时：**不生成结果**，列出冲突对（如"王五固定 1-1 座"与"李四固定 1-1 座"），提供"降级为强烈/改规则/手动指定"三条出路。
- 硬约束无法满足（如"两人必须同桌"但布局是单桌）：提示"当前布局不支持该规则"，并给"切换为双人桌布局"的快捷跳转。
- 软约束未满足：不影响生成，但在结果页以红色列出，并给出"提高权重重排"的一键操作。

### 5.6 性能目标

60 人 / 60 槽 / 12 条规则：单次求解 ≤ 1.5s（Web Worker 内执行，UI 不卡），增量"换一个人"的重优化 ≤ 200ms。
语义预处理：缓存命中 ≤ 50ms；首次联网（批量 embedding + 标签抽取）≤ 3s；接口超时 4s 自动降级，不阻塞排座。

## 6. 交互与动效规范

动效原则：**有物理感、不炫技、服务于理解**。所有动效可被"精简/关闭"设置统一降级。

| 场景 | 效果 | 时长 / 曲线 |
| --- | --- | --- |
| 排座结果入场 | 座位按排从左到右 40ms stagger 淡入 + 轻微上浮 | 340ms，`cubic-bezier(0.22, 1, 0.36, 1)` |
| 拾起座位 | 缩放 1.05、阴影加深、跟随指针倾斜 ≤3°、其余座位透明度 0.55 | 160ms |
| 目标位指示 | 描边呼吸光晕 + 占位轮廓 | 循环 1.2s |
| 放置交换 | 两卡片沿弧线交换位置，弹簧回正 | spring(stiffness 320, damping 30) |
| 非法放置 | 卡片抖动 2 次、红色禁止描边、toast 说明原因 | 280ms |
| 撤销 | 反向位移 + 轻微淡出淡入 | 260ms |
| 视角翻转 | 整画布 3D Y 轴翻转 180°，文字先淡出再淡入，避免镜像文字 | 600ms |
| 布局参数修改 | 座位重排为 FLIP 位移动画，不闪烁 | 420ms |
| 计算中 | 画布上方扫描光线掠过 + 进度环 | 循环至完成 |
| 规则满足度变化 | 数字滚动 + 环形进度条描边动画 | 500ms |

细节要求：
- 拖拽使用 `dnd-kit` 做命中检测与排序，`Framer Motion` 做布局动画（`layout` + `LayoutGroup`），避免手写 transform 冲突。
- 拖拽期间禁用文本选中，指针离开窗口自动取消并回弹。
- 所有可点元素具备 hover/focus/active 三态；键盘焦点环清晰可见。
- 大列表（>80 座）时关闭 stagger，仅保留位移动画，保证 60fps。

### 8.4 关键交互实现要点

- 交换动画：先 `layoutId` 保持身份，交换后由 `LayoutGroup` 计算 FLIP；拖动中卡片用 portal 渲染在顶层，避免被容器 `overflow` 裁剪。
- 高频拖拽：拖动位移只写 `transform`（GPU 合成层），状态更新节流到 `requestAnimationFrame`，松手才提交 store。
- 撤销栈：记录 `{type, from, to, before, after}` 的轻量指令，而非整棵快照。
- 打印：单独渲染一份 `print-only` DOM（A4 版式），而非打印主画布。

### 8.5 AI 集成设计（硅基流动）

**调用链**

```
特点文本 → 本地缓存查询 → 未命中 → Rust command（ai_extract_tags / ai_embed）
        → SiliconFlow API（https://api.siliconflow.cn/v1）
        → 结果写缓存 → 返回领域层 → 参与评分
```

**接口约定**

| 用途 | 接口 | 模型 | 约束 |
| --- | --- | --- | --- |
| 标签抽取 | `/v1/chat/completions` | Qwen 系（`temperature=0`，`response_format=json_object`） | 单次批量 ≤ 20 条文本，输出严格 JSON |
| 语义向量 | `/v1/embeddings` | `BAAI/bge-m3` | 单次批量 ≤ 64 条，1024 维 |

**工程约束**

- 超时 4s，失败重试 1 次（500ms 退避），仍失败立即降级；**绝不阻塞排座主流程**。
- 请求体仅含特点文本，不含姓名/学号/班级名；日志只记录 hash 与耗时，不记录原文。
- API Key 由老师在设置页填写，加密存于 Stronghold；未配置时功能可见但标注"未配置"，核心功能不受影响。
- 模型名参与缓存 key：模型升级后旧缓存自动失效并重算，避免向量空间不一致导致的错误匹配。
- 提供「AI 用量」面板：本月调用次数、成功率、预估费用；异常或超额前提醒。
- **明确不做**：不把座位表或学生名单发给模型；不做流式输出；不做多轮对话；不让模型输出座位坐标。

## 12. 风险与待确认问题

### 12.1 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 规则过多导致冲突频繁 | 老师排不出结果 | 默认只开 4 条内置规则；冲突给一键降级 |
| 老师对"算法结果"不信任 | 弃用智能排座 | 每个座位提供可读理由 + 满足度可视化 |
| 拖拽在低配机器掉帧 | 手感差 | transform-only + 关闭 stagger + 降级动效 |
| 排座结果主观性强（人际关系不可量化） | 无法完全满足 | 明确"算法给建议，最终由老师决定"；手动调整即视为权威 |
| AI 服务不可用 / Key 失效 | 语义功能失效，老师误以为软件坏了 | 显著降级提示 + 本地词典兜底 + 设置页一键连通性测试 |
| 语义归并偏差（该合的没合、该分的分错） | 排座结果被质疑 | 语义簇地图可视化 + 手动合并/拆分 + 相似度阈值可调 |
| 特点文本上云引发隐私顾虑 | 老师不敢用 | 只传文本、默认严格脱敏、AI 可整体关闭 |
| 模型/供应商变更导致向量漂移 | 缓存失效、结果前后不一致 | 模型名写入缓存 key，切换模型强制重算并提示 |
| AI 费用不可控 | 学校不愿承担 | 缓存优先 + 批量请求 + 用量面板 + 免费额度耗尽提醒 |

### 12.2 开放问题（请确认）

1. 单个班级人数上限按 **80 人** 设计是否够用？是否有 100 人以上的大班场景？
2. **API Key 归属**：由老师自备 Key（成本透明、推荐）还是产品内置代理服务（要承担费用与合规责任）？
3. **Embedding 模型**：先用 `BAAI/bge-m3`（多语言、长文本、单价略高），还是 `BAAI/bge-large-zh-v1.5`（更便宜、更偏中文）？建议先各跑 100 条真实标签做效果对比再定。
4. **严格脱敏默认开还是关**？开启后"和班长坐一起"这类文本会丢失人名，语义略降但隐私更稳。
5. 单桌模式（无同桌）下，"男女搭配"应退化为**相邻交替**还是**直接忽略**？
6. 是否需要**学生头像**（导入照片或首字母圆形色块）？会影响画布信息密度。
7. 老师是否需要给座位**标座位号**（1–48）并支持导出时显示？还是只按"第 X 排第 Y 组"描述？
8. 是否需要"**性别分列/分排**"这类强需求（如男生靠窗、女生靠门）？
9. 讲台方向是否只需要上下两种，还是也需要左右（横排教室）？
10. 是否需要「**导入后自动去重/合并同名学生**」的处理策略？
